2. Etapa 3 — PeriodicTask órfã do Beat

O que é

A task process_scheduled_notifications foi comentada no código, mas o agendador persiste o schedule fora do código. Sobra uma entrada órfã apontando para uma task que não existe mais → KeyError no dispatch do Beat. Era o maior ruído do produto (~1.640 ev — clusters BACKEND-1H / WORKER-1F).

Estado atual no repositório (confirmado ao vivo)

  • worker/apps/notifications/tasks/notification_tasks.py — process_scheduled_notifications e cleanup_old_notification_logs estão comentadas. ✓ (foi o que criou a órfã)
  • worker/config/celery.py — beat_schedule tem 8 entradas e nenhuma é a task removida. ✓
  • backend/config/celery.py — não define beat_schedule e agora tem comentário explícito explicando o porquê (resultado do bug #53659). ✓
  • Onde a órfã realmente vive: o Beat roda com PersistentScheduler → arquivo /tmp/celerybeat-schedule (shelve), persistido pelo volume /tmp. Não é o DB.
⚠ Correção ao xlsx: o cronograma assumia a órfã no DB (django_celery_beat.PeriodicTask). O código mostra que django_celery_beat está em INSTALLED_APPS mas não é o scheduler em uso — a órfã está no arquivo shelve. Verificar os dois por garantia.

Meios para resolver

  1. Diagnosticar onde a órfã está — inspecionar /tmp/celerybeat-schedule* no container do beat e checar PeriodicTask.objects.filter(task__icontains='process_scheduled_notifications') no DB.
  2. Expurgar (entrega real, #53707):
    • Se for o arquivo shelve (mais provável): parar o beat, rm -f /tmp/celerybeat-schedule*, subir de novo — recria a partir do beat_schedule do código.
    • Se houver linha no DB: data migration idempotente (PeriodicTask…filter(task__endswith='process_scheduled_notifications').delete()), versionada.
  3. Travar a fonte de verdade — manter o file scheduler; não misturar com DatabaseScheduler (a mistura é o que gera órfãs).
  4. Validar — sem mais KeyError no dispatch; queda dos clusters BACKEND-1H / WORKER-1F no Sentry (~1.640 → ~0). Teste de guarda: cada task do beat_schedule registrada em app.tasks.
⚠ Runtime: o passo 2 não versiona em código. Apagar arquivo de ambiente / rodar migration de delete deve ser confirmado antes de executar.

3. Etapa 5 — Consolidar o init do Sentry no init_sentry

O que é
