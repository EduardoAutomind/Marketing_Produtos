2. set-commits --auto (suspect commits) — NÃO CUMPRIDA

Não há sentry-cli em nenhuma das 6 pipelines. SENTRY_RELEASE é só uma env var consumida pelo SDK em runtime; ninguém associa commits ao release. Sem isso, o Sentry não aponta o “suspect commit” — que é o ganho da etapa. Confiança: alta.

3. Isolar pipelines Azure — NÃO CUMPRIDA

Reler o objetivo: não há agente de máquina dev — tudo roda no pool hospedado Azure Pipelines. O risco real é dev e prod compartilharem a mesma pipeline sem gate.

  • 0 Environments no projeto (_apis/pipelines/environments → count: 0) ⇒ nenhum gate de aprovação/checks antes de prod. Confiança: alta.
  • dev e main na mesma pipeline — prod gated só por condition: eq(Build.SourceBranchName,'main') (backend:197, worker:165). Push na main publica em prod sem aprovação.
  • Worker dev usa a connection do backend: sshEndpoint: "backend-dev" (worker…yml:115).
  • Connections SSH em uso (dos YAMLs): backend-dev, backend-prod, ssh-service-connection-worker. Config interna não verificável (PAT sem escopo → 401). Flag: Não sei.

Veredito #3: NÃO CUMPRIDA — há separação por componente, mas nenhum isolamento dev↔prod.

6. Achados extra (reais)

  1. Segredo embutido + history overwrite: sync Azure→GitHub com https://rochaTarcisio:$(GITHUB_TOKEN)@github.com/… e git push --force após rm -rf .git; git init (frontend:113-116, backend:103-106, worker:98-101).
  2. Modelo de deploy real: Azure testa → espelha no GitHub (force push) → SSH no droplet → git pull + docker compose/systemctl. Build acontece no servidor. Isso muda onde o set-commits deve rodar (precisa do histórico git — melhor no CI, antes do mirror destrutivo).
  3. AutoChecker_APP é só placeholder hoje.

7. Plano de resolução (na ordem)

Passo 1 — Frontend: fechar release + org/project

Corrigir org/project nos next.config.js e definir SENTRY_RELEASE=autochecker-frontend@<hash> no build, alinhando com backend/worker.

Passo 2 — set-commits no CI (os 3 serviços)

sentry-cli releases new "<comp>@$HASH"
sentry-cli releases set-commits "<comp>@$HASH" --auto
sentry-cli releases finalize "<comp>@$HASH"

Rodar antes do rm -rf .git (senão perde o histórico). Token via SENTRY_AUTH_TOKEN secreto do CI.

Passo 3 — Corrigir o bug do worker em prod

git pull origin dev → main (linha 183) e gravar em worker/.env.prod, não .env.dev (linha 188).

Passo 4 — Isolamento dev↔prod de verdade

Criar Environments (autochecker-prod/-dev) com approval check em prod; converter os jobs de prod em deployment jobs (environment:); separar a connection do worker da do backend.

Passo 5 — Decidir o frontend canônico

Há duas pipelines de frontend vivas apontando para repos diferentes. Definir a de produção e desabilitar/arquivar a outra.
