Source maps ausentes — o erro nº1 (Object.s) é nome minificado, inútil para debug. Subir source maps no build do frontend é quick win.

libwkhtmltox — feature de exportação/relatório em PDF quebrada em produção por dependência nativa faltando no container. Poucos usuários afetados só porque poucos usam PDF, mas a feature está 100% inoperante.

Failed to fetch (14 usuários) — maior dispersão; investigar correlação com as telas lentas (Programações p95 5 s pode estar estourando timeout).

6. Síntese e recomendações

  1. Programações é o coração e o gargalo. Tela mais usada (~50% da navegação) e a mais lenta (p95 5,2 s). Otimizar aqui tem o maior retorno de UX. Provável causa: GET /api/v1/programs (6,1k chamadas) sem paginação/cache eficiente.
  2. Preferências de usuário super-chamadas (14k+). Investigar leitura/escrita repetida por tela → cachear / consolidar.
  3. Subir source maps do frontend — sem isso o erro nº1 de produção é cego.
  4. Corrigir libwkhtmltox no container de produção (feature de PDF morta).
  5. Backend sem telemetria (item já levantado). Hoje a análise de API é indireta; com SENTRY_DSN na release do backend, veremos latência/erro server-side direto.
  6. Higiene de ambiente: segue o production órfão (1,5k) convivendo com prd; backend tem dev E Development. Padronizar.
